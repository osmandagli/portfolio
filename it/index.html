L4 Trasporto · la mia tesi magistrale

Tesi

Accelerating a Media-over-QUIC Relay with AF_XDP Kernel-Bypass Networking

Osman Bugra Dagli · Politecnico di Milano · gen 2025 – oggi

Media over QUIC (MoQ) è un protocollo IETF emergente per la distribuzione di media in diretta, e i relay ne sono il cuore. Ogni pacchetto che inoltrano attraversa lo stack di rete del kernel. Questa tesi misura quanto costa nel relay moxygen di Meta e toglie il kernel da quel percorso.

Un’analisi del tempo CPU basata su perf mostra che il relay è limitato dalla CPU di un singolo core, a circa l’1% della velocità di linea da 100 Gbit/s della NIC, e che l’I/O dei pacchetti nel kernel occupa il 16–29% del tempo attivo di quel core. Ho costruito un fast path AF_XDP e l’ho collegato allo stack QUIC tramite un punto di iniezione dei socket: il punto in cui il server sceglie quali socket UDP usa QUIC. L’intero percorso UDP RX/TX del relay ora passa per AF_XDP senza modificare la logica di inoltro del relay; l’unica modifica al server sono poche righe, attivabili con un flag, che installano la socket factory AF_XDP.

Il margine è stato misurato prima, con un microbenchmark del percorso di ricezione sullo stesso hardware e senza lavoro applicativo per pacchetto: su un core, AF_XDP zero-copy riceve circa 2,4 volte più pacchetti al secondo del percorso kernel ottimizzato.

microbenchmark del percorso di ricezione, un core (milioni di pacchetti/s · UDP da 1500 byte · nessun lavoro per pacchetto · Intel E810)

kernel · recvmmsg + GRO (ottimizzato) ~0,65
AF_XDP · zero-copy ~1,55

~2,4× per core

  • Un microbenchmark del percorso di ricezione sull’hardware del testbed: AF_XDP zero-copy raggiunge ~1,55 Mpps su un singolo core, contro ~0,65 Mpps di un percorso kernel ottimizzato (recvmmsg + GRO)

Miosix resistente alle radiazioni

LLVM · STM32 · 2026

In orbita, una particella carica può invertire un bit in un registro o in RAM. È un single-event upset, e il codice continua a girare con un valore sbagliato. ASPIS è un plugin LLVM dell’HEAPLab del Politecnico di Milano che protegge il codice da questo problema a livello della rappresentazione intermedia (IR) di LLVM. L’ho integrato nella build di Miosix, un RTOS embedded, così il kernel stesso viene compilato in versione protetta per un STM32F407.

Prova: clicca un bit qualsiasi di x per colpirlo con un raggio cosmico. EDDI (error detection by duplicated instructions) tiene una copia ombra di ogni valore e confronta le due prima di usarlo.

x 0x2A
x′ ombra 0x2A

icmp eq x, x′ è vero, quindi l’esecuzione continua.

  1. C / C++
  2. clangemits LLVM IR
  3. llvm-link
  4. ASPIS passesEDDI + CFCSS
  5. codegen
  6. .elf → .binobjcopy
  7. STM32F407
  • Un modulo CMake che fa passare qualsiasi target per la pipeline clang → opt → link e salta automaticamente i file assembly
  • Ogni pass si può scegliere dallo script di build: duplicazione dei dati (eddi, reddi, seddi, fdsc) e controllo del flusso (cfcss, rasm, inter-rasm, racfed)
  • Ho compilato l’intero kernel con ASPIS, poi sono passato a una protezione selettiva con annotazioni sullo scheduler
  • Un toolchain file clang che può puntare a qualsiasi installazione di LLVM, più un passaggio objcopy che produce un .bin pronto da flashare

containerrt

Go · mar 2026

Un container runtime minimale scritto da zero sulle primitive Linux, senza runc né libcontainer. Volevo sapere esattamente cosa fa docker run prima che il processo parta.

  1. clone()NEWUTS · NEWPID · NEWNS
  2. pivot_roothost root fully unmounted
  3. tmpfs /devessential device nodes
  4. cgroup v2limits applied by parent
  5. pipe barrierchild waits for setup
  6. exec
  • Isolamento con i namespace UTS, PID e mount
  • pivot_root invece di chroot: la root dell’host viene smontata, non solo nascosta
  • Un /dev tmpfs effimero con i soli device node essenziali
  • Una barriera di sincronizzazione su pipe tra padre e figlio garantisce che il processo parta già dentro i limiti cgroup v2, senza race con il setup
  • Un vero init: raccoglie gli zombie, inoltra SIGINT/SIGTERM ed esce con il codice del processo (128 + segnale)
  • Testato con tentativi di evasione, monitoraggio di pids.current e OOM kill sotto memory.max

conntracker

eBPF/XDP · mag 2025

Connection tracking e fingerprinting TCP che girano nel kernel, a livello XDP, prima ancora che lo stack di rete allochi un sk_buff.

  • Macchine a stati TCP e UDP in eBPF, con metriche per connessione
  • Estrae le sequenze di opzioni TCP (MSS, SACK, timestamp, window scale) per il fingerprinting di sistema operativo e stack
  • Un demone user-space in C carica una configurazione YAML, aggancia il programma ed espone statistiche e ban list via HTTP
  • Count-Min sketch e filtri di Bloom per un filtraggio rapido a soglia con memoria limitata
